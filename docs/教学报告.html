第 0 章 · 五分钟看懂

我们要做一个什么东西

DocPilot 是一个"能查着自己家资料回答问题"的助手。听起来普通，但它有一个别人没有的特性：

它能判断自己找的资料够不够用。不够就换个问法重新找一遍，而不是硬编一段答案糊弄你。

用户视角长这样

你问：账号被锁了多久才能再登

① 路由 → 判定"需要查资料"
② 检索 → 用原问题召回 4 条，但都不太对
③ 评分 → 4.6 分，低于及格线 6.5
④ 重写 → 「账号被锁定 多久才能再登」（把口语换成文档用词）
② 检索 → 重新召回，这次命中了正确文档
③ 评分 → 6.9 分，达标，继续
⑤ 生成 → 带引用编号的答案
⑥ 反思 → 发现有"建议"类表述，属于敏感内容
⑦ 人工审核 → 图暂停在这里，等人点通过
⑧ 定稿 → 输出最终答案

上面这段不是编的 —— 它是项目真实跑出来的执行轨迹，你在 S6 章节能看到一模一样的输出。

技术栈一览

层选型为什么

第 1 章 · LangGraph 到底在解决什么问题

先说清楚它和 LangChain 的关系

很多人在这儿绕不清。一句话：

LangChain 是"工具箱"，LangGraph 是"流水线调度器"。

LangChainLangGraph
核心抽象链（Chain）、组件（Component）图（Graph）、节点（Node）、状态（State）
流程形状一条线，从前往后任意有向图，可以有分支和环
适合什么"输入 → 处理 → 输出"的固定流程需要判断、循环、暂停、恢复的 Agent 流程
能不能暂停等人基本不行可以，而且能停几天

它们不是取代关系 —— LangGraph 内部照样在用 LangChain 的消息类型、模型接口、工具抽象。 你在这个项目里会同时用到两者。

为什么 Agent 需要"图"，而不是"链"

想想一个人干活的真实过程：

  • 看到问题 → 判断要不要查资料（分支）
  • 查了资料 → 发现不对 → 换个词再查（循环）
  • 写好了 → 拿不准 → 请同事确认一下（暂停 + 恢复）

"链"只能表达第一条。第二条和第三条，链做不到 —— 因为链的定义就是"从前往后走一遍，走完就结束"。

而图天然支持这三件事：节点是步骤，边是流向， 条件边是岔路口，回边是循环。

核心心智模型：图 = 状态 + 节点 + 边

概念英文人话解释
状态State一张在整个流程里传来传去的共享便签纸。每个节点都能读，也能往上写。
节点Node一个函数。读便签、干一件事、往便签上写点东西，然后返回。
边Edge规定下一步去哪儿。普通边是"一定去"，条件边是"看情况去"。

就这三个概念。整份报告后面讲的所有东西，都是这三个概念的组合变化。

一张图看懂我们的项目

START → ① 路由判断
├─ 不用查资料（闲聊） ──────→ ⑤ 生成答案
└─ 需要查资料 → ② 检索 → ③ 评分
① 分数不够 → ④ 重写查询 ↺ 回到 ②
② 分数够 → ⑤ 生成答案 → ⑥ 反思自查
├─ 敏感内容 → ⑦ 人工审核 → ⑧ 定稿 → END
└─ 普通内容 ──────────────→ ⑧ 定稿 → END

别看这张图有点大 —— 拆开看每个部分都很简单，我们会在 S1～S6 里一部分一部分加上去。

🎯 面试考点

问：LangGraph 和 LangChain 什么关系？为什么要用 LangGraph？

答题要点分三层：

  1. 定位不同：LangChain 提供模型、工具、消息这些"零件"；LangGraph 提供把这些零件按有向图组织起来跑的"调度器"。两者是互补，不是替代。
  2. 能力边界：链式结构只能表达线性流程。Agent 本质上需要"判断—行动—再判断"的循环，还经常需要人工介入，这些链做不到。
  3. 最实际的差异：图可以把执行状态持久化，所以能暂停、能续跑、能回退。链做不到这一点。

第 3 章 · 术语逐个击破

这一章只讲最核心的 10 个词，每个都配一个类比。 剩下的术语在 附录 A 里汇总成表，需要时去查。

1 · State（状态）

类比：一张在会议室里传阅的共享便签纸。

每个参会的人（节点）拿到它，看一眼上面写了什么（读状态）， 写上自己的结论（写状态），然后传给下一个人。 整场会议下来，便签上积累了完整的信息。

在代码里它是一个 TypedDict， 每个字段就是便签上的一行。

2 · Node（节点）

类比：一个工人，只干一件事。

它是一个普通的 Python 函数：

python 
def retrieve(state) -> dict:
    """读状态 → 干活 → 返回要更新的字段"""
    query = state["question"]          # 读
    chunks = retriever.retrieve(query)      # 干活
    return {"documents": chunks}           # 写（返回增量，不是完整状态！）

注意最后一行：返回的是增量，不是完整状态。这是新手第一个容易绕的地方。

3 · Edge（边）

类比：两个工位之间的传送带。

add_edge("A", "B") 的意思是" A 干完一定轮到 B "。 传送带是固定的，没有判断。

4 · Conditional Edge（条件边）

类比：路口的红绿灯，或者流水线上的质检员。

它不看"上一步是什么"，而是读一眼当前状态，然后决定往哪走：

python 
def after_grade(state) -> str:
    if state["retrieval_score"] >= 6.5:
        return "generate"     # 资料够用，去生成答案
    return "rewrite"          # 资料不行，去重写查询

返回的字符串，会通过一张映射表对应到目标节点名。 有了条件边，流程才有了"判断"。

5 · Reducer（归约函数）★

类比：多人同时往同一张便签上写字，该听谁的？

这是新手最容易踩坑、也是面试最容易考到的一个概念。

节点返回的字段要合并进已有状态，合并规则就是 reducer：

写法语义典型场景
某字段: int覆盖计数器、当前答案、当前查询 —— 新值盖掉旧值
messages: Annotated[list, add_messages]追加多轮对话历史 —— 新消息接在旧消息后面
数字: Annotated[int, operator.add]累加用了几次工具、总共多少 token

那个 Annotated[...] 是 Python 的语法，作用是在类型标注上"挂"一条额外信息（这里挂的就是合并规则）。

❌ 一个真实踩过的坑

我一开始给"执行轨迹"字段也加了 add 类型的 reducer，觉得"日志嘛，当然要累加"。 结果加上检查点之后炸了：

因为检查点会让同一个会话的状态跨轮保留，第二轮提问时第一轮的轨迹还在， 第三轮又叠上去，几轮之后界面上就是一坨。

教训是：加 reducer 之前先问自己一句 —— 这个字段是希望"跨轮累积"，还是"每轮重来"？ 历史消息要累积，执行轨迹要重来。项目里对应的处理在 src/docpilot/state.py 的注释里写得很清楚。

6 · Checkpointer（检查点）

类比：Word 的自动保存。

图每往前走一步，就把当前完整状态存一份，用 thread_id 当作存档编号。

带来三个能力：

  • 多轮记忆 —— 同一个 thread_id 再调用，会自动把历史读回来
  • 断点续跑 —— 进程崩了、人走开了，状态都还在
  • 时间旅行 —— 能列出所有历史存档，回到任意一步重跑
实现存在哪什么时候用
InMemorySaver内存开发和测试，重启就没了
SqliteSaver本地文件单机演示够用
PostgresSaverPostgreSQL生产环境标配，支持并发

7 · thread_id（会话编号）

类比：聊天软件里的"会话窗口"。

同一个 thread_id 反复调用 → 接着上次聊。 换一个 thread_id → 全新会话，互不影响。

它本质上就是检查点表里的一个主键。两个用户用两个不同的 ID， 状态天然隔离，不需要额外加锁 —— 这是 LangGraph 支持多用户的设计基础。

8 · interrupt() 与 Command(resume=) ★

类比：审批流程。

你的申请提交上去，流程走到"领导审批"这一步就停住了。 人事专员去问领导，领导说"同意"，流程从刚才停的地方继续走。

python 
# 停住：把待审内容交给外面的人
from langgraph.types import interrupt

def human_review(state):
    decision = interrupt("请审核这段内容是否可发送")   # ← 执行到这里暂停
    return {"approved": decision == "approve"}       # ← 恢复后从这里继续

# 恢复：把人的决定送回去，它就成了 interrupt() 的返回值
graph.invoke(Command(resume="approve"), config=config)
⚠️ 两个必须记住的前提

1. 必须先配 checkpointer，否则状态没地方存，interrupt 直接报错。
2. 必须用同一个 thread_id 恢复，它是找回这次对话的唯一线索。

还有一个容易踩的细节：节点恢复时是从头重新执行的， 不是从 interrupt() 那一行接着跑。所以 interrupt() 之前 别放"发消息、写数据库"这类有副作用的操作，否则会重复执行。

9 · Tool（工具）与 ToolNode

类比：模型是"动嘴的"，工具是"动手的"。

模型本身不会执行任何代码，它只会输出一句"我想调用 xxx，参数是 yyy"。 真正去跑函数的是 ToolNode。这个分工一定要分清楚。

写工具时有两条铁律：

  • 函数的 docstring 就是给模型看的说明书。写"查询知识库"没用，要写清楚"什么时候该用它、参数怎么填"。
  • 参数必须写类型注解，框架据此自动生成 JSON Schema 给模型看。

10 · recursion_limit（递归上限）

类比：游乐场过山车的"最多坐 25 分钟"提示。

图里有环，就有无限循环的风险。LangGraph 默认最多走 25 步， 超过就抛 GraphRecursionError。

注意 LangGraph 里的"一步" = 访问一个节点。 一次工具往返要算两步（模型节点 + 工具节点）。 所以 25 步其实只有大约 12 次工具调用。

🎯 面试考点

问：reducer 是干什么的？能举个例子说明不加会怎样吗？

这是本章最重要的一题，建议连着"踩坑故事"一起讲：

  1. 先给定义：reducer 决定同一字段被多次写入时的合并语义，默认是覆盖。
  2. 再说必要性：多轮对话必须用 add_messages，否则第二轮的历史消息会把第一轮覆盖掉，模型瞬间失忆。
  3. 最后讲那个坑（这段最能体现你真的做过）：不是所有列表都该加 reducer。执行轨迹字段加了 add 之后， 因为检查点会跨轮保留状态，轨迹会一轮轮叠加。所以判断标准是"这个字段要跨轮累积，还是每轮重置"。

S1 · 最小状态图

阶段 1 对应文件：src/docpilot/graphs/s1_basic.py　跑它：python src/docpilot/graphs/s1_basic.py

① 一句话目标

先别管大模型聪不聪明、检索准不准。只搞明白一件事：状态是怎么在节点之间流动的。

② 图示

START → ① 分类 → ② 回答 → ③ 润色 → END

一条直线，三个节点，没有任何分支和循环。先建立最朴素的肌肉记忆。

③ 代码

第一件事：声明状态长什么样。

python 
from typing import Annotated, TypedDict

class BasicState(TypedDict, total=False):
    question: str                          # 用户的问题
    category: str                          # 分类结果
    answer:   str                          # 回答（会被覆盖两次）
    trace: Annotated[list[dict], operator.add]  # 执行轨迹（累加）

total=False 表示所有字段都是可选的 —— 初始调用时不用把所有字段都填上。

第二件事：写节点。一个节点就是一个函数：

def classify(state: BasicState) -> dict:

    if any(w in question for w in ("接口", "报错", "部署")):

        category = "业务问题"
    else:
        category = "其他问题"

    # 只返回「要更新的字段」，不是完整状态
    return {
        "category": category,
        "trace": [{"step": "① 分类", "detail": f"判定为「{category}」"}],
    }

④ 逐段拆解

为什么要 compile()？

因为图在编译时才会做校验：节点名有没有重复、边连的节点是否存在、 状态字段的 reducer 有没有冲突。把错误暴露在编译期，而不是运行到一半才炸。 编译之后还会生成一个可以画出来的图结构（就是上面那张"图的形状"）。

为什么分类节点故意不调大模型？

为了让这一阶段的注意力完全集中在"图"上。分类用关键词规则就够 —— 跑得快、结果稳定、没有任何不确定性。等你把图的机制吃透了， 再考虑把这种小判断换成模型，那时你已经知道图是怎么跑的了。

这是我自己很推崇的学习方式：一次只引入一个新的不确定性。 同时引入"图"和"大模型"两个新东西，出问题时你根本不知道是谁的锅。

被覆盖 vs 被累加，怎么看出来的？

看这个执行顺序：

  • answer 字段先被"回答"节点写成原始回答
  • 然后被"润色"节点整个覆盖成"【分类】+ 原始回答"
  • trace 字段则是三个节点各追加一条，最后有 3 条

同一个 dict 返回，两种完全不同的合并行为 —— 差别就在状态定义里那个 Annotated[..., operator.add]。

⑤ 跑起来看什么

输出 
── 执行轨迹 ──
  ① 分类：判定为「技术问题」
  ② 回答：已调用模型生成原始回答
  ③ 润色：已拼接分类前缀（answer 被覆盖）

── 最终状态里的字段 ──
  question = '接口调用报错 RATE_LIMITED 是什么意思？'
  category = '技术问题'
  answer   = '【技术问题】...'

重点不是答案对不对（这一阶段的答案很粗糙，很正常），而是：

  1. 轨迹有 3 条 → 三个节点都跑到了，顺序对
  2. 最后的 answer 带着分类前缀 → 后面读到了前面写的值，状态流动是通的
🎯 面试考点

问：LangGraph 的基本构建流程是什么？

答：四步 —— 定义状态（TypedDict）、注册节点（纯函数）、连接边（普通边 + 条件边）、编译。 编译这一步会做静态校验，把结构性错误提前暴露出来。

追问：节点函数的返回值有什么讲究？

答：返回的是增量字典，不是完整状态。LangGraph 拿它去合并进全局状态， 合并规则由字段的 reducer 决定。默认是覆盖，用 Annotated[x, add] 可以改成累加。

① 一句话目标

把主动权交给模型：让它自己决定要不要调工具、调哪个、传什么参数。

② 图示

我们只给它两个工具：
🔍 search_knowledge_base 查内部知识库
🧮 calculator 算数

③ 代码

先写工具。注意 docstring 不是写给人看的，是写给模型看的：

python 
from langchain_core.tools import tool

@tool
def search_knowledge_base(query: str, top_k: int = 4) -> str:
    """在公司内部知识库中检索资料。

    当用户的问题涉及产品功能、接口用法、操作流程、技术规范、参数配置、
    故障排查等需要依据内部文档才能准确回答的内容时，使用这个工具。
    不要用它来回答闲聊或通用常识问题。

    参数：
        query: 检索用的查询语句。建议用陈述式的关键词组合，
               比如"登录失败 排查 步骤"，而不是"登录失败怎么办？"。
        top_k: 返回多少条资料，默认 4 条。
    """
    retriever = get_retriever()
    chunks = retriever.retrieve(query, top_k=top_k)
    return "\n\n".join(f"[{i}] {c['content']}" for i, c in enumerate(chunks, 1))

④ 逐段拆解

docstring 到底有多重要？

非常大。模型看到的"工具列表"就是函数签名 + docstring 自动生成的 JSON Schema。 你写"这是一个查询函数"，模型就完全不知道什么该用它； 你写清"涉及内部文档的问题用它，闲聊别用"，模型才可能选对。

经验值：docstring 控制在 1024 字符以内。太长的说明应该挪到系统提示词里，别塞进工具描述。

工具的参数写 query: str 有什么讲究？

类型注解会被转成 JSON Schema 给模型看。如果不写，模型就得瞎猜参数名和类型， 调用成功率会明显下降。

⚠️ 一个真实的版本坑（面试加分项）

你如果搜"LangGraph 怎么搭 Agent"，大概率会看到这个写法：

from langgraph.prebuilt import create_react_agent

项目里的做法是写一个"版本兼容垫片"：优先试新 API，没有就退回旧 API。 这多写了十几行，但别人换环境跑不起来的时候你还能跑。

⑤ 跑起来看什么

看它决定调用哪个工具，以及工具结果有没有被正确带回对话：

输出 
── 完整消息链路 ──
  [HumanMessage] 接口返回 429 是什么意思？该怎么处理？
  [AIMessage] 想调用工具：['search_knowledge_base']      ← 它自己决定的

消息链路里那四种消息类型，是理解 Agent 运行过程的关键：

类型代表什么
HumanMessage用户说的话
AIMessage模型说的话（可能带 tool_calls，表示"我想调工具"）
ToolMessage工具执行完的结果，回灌给模型
SystemMessage系统提示词，设定模型的身份和规则
🎯 面试考点

问：LangGraph 的 API 分几层？你平时用哪层？

答：三层，自顶向下是 ——

  1. 预构建图（create_agent）：一行搞定标准 Agent 模式，经过大量真实项目打磨，出错概率最低
  2. Agent Node 中层 API：保留对循环的控制，但省去手写细节
  3. 构建图底层 API（StateGraph）：完全手动，多分支、循环、人工介入都能显式表达

然后给出你的判断标准："能用高层就用高层，只有默认行为确实不满足业务需求时才下沉到底层。" 这句话很关键 —— 它说明你不是为了炫技而手写图。

S3 · 把 S2 拆开，手写一遍

阶段 3 对应文件：src/docpilot/graphs/s3_react.py　跑它：python src/docpilot/graphs/s3_react.py

① 一句话目标

搞清楚 create_agent 内部到底画了什么图。会用它，也要能拆它。

② 图示

START → agent（模型）
↓ 条件边：模型输出里有 tool_calls 吗？
├─ 有 → tools（执行工具） ↺ 回到 agent
└─ 没有 → END （说明模型给出了最终答案）

③ 代码

python 
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode

class ReactState(TypedDict, total=False):
    messages: Annotated[list[AnyMessage], add_messages]   # ← 必须带 reducer

def call_model(state):
    """节点1：模型负责「想」—— 决定回答还是调工具"""
    model = llm.bind_tools(ALL_TOOLS)          # 告诉模型有哪些工具可用
    response = model.invoke([SystemMessage(content=REACT_SYSTEM), *state["messages"]])
    return {"messages": [response]}

def should_continue(state) -> str:
    """条件边：看模型最后说了什么，决定下一步"""
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"       # 想去调工具
    return END                # 没有工具调用 → 它已经给出答案了，结束

builder = StateGraph(ReactState)
builder.add_node("agent", call_model)
builder.add_node("tools", ToolNode(ALL_TOOLS))   # 节点2：工具负责「做」

builder.add_edge(START, "agent")
builder.add_conditional_edges(
    "agent", should_continue,
    {"tools": "tools", END: END},       # 返回值 → 目标节点
)
builder.add_edge("tools", "agent")          # ← 这条回边，就是"循环"

graph = builder.compile()

④ 逐段拆解

整体就是：两个节点 + 一条条件边 + 一条回边。 create_agent 帮你省掉的，其实只有这么点东西。

为什么 messages 必须带 reducer？

因为循环里每一步都在追加消息。如果不加 add_messages， 第二步的工具结果会把第一步的模型输出覆盖掉 —— 循环当场断掉， 模型看到的消息列表里永远只有最新一条。

条件边的返回值可以直接是 END。

映射表里写 {END: END} 意思就是"返回 END 就直接结束流程"， 不用再写一个专门的终止节点。

ToolNode 做什么？

它读取最后一条消息里的 tool_calls，逐个执行对应的函数， 把结果包装成 ToolMessage 追加到消息列表。 模型输出的只是"我想调用 xxx"，真正执行的永远是 ToolNode。

回边会不会死循环？

会，所以需要 recursion_limit 兜底：

python 
result = graph.invoke(
    {"messages": [HumanMessage(content=q)]},
    config={"recursion_limit": 12},     # 最多走 12 步，超了抛异常
)

LangGraph 里的"一步" = 访问一个节点。一次工具往返算两步（模型节点 + 工具节点）， 所以 12 步大约等于 5 次工具调用。这个换算关系面试常被追问。

⑤ 跑起来看什么

输出 
── 消息流转过程 ──
  1. [HumanMessage] → 连续输错密码 5 次会怎么样？...
  2. [AIMessage]    → 决定调用 ['search_knowledge_base']
  3. [ToolMessage]  → 返回 1532 字结果
  4. [AIMessage]    → 根据知识库中的资料，整理如下：...

两条 AIMessage 之间夹着一条 ToolMessage —— 这正好对应"模型想 → 工具做 → 模型再想"的一个完整循环。

🎯 面试考点

问：ReAct 循环在生产环境可能出什么问题？

答四条，每条都带解法，层次感立刻出来：

问题解法
死循环（反复调同一个工具）设 recursion_limit；在条件边里加"同一个工具调用超过 N 次就强制结束"
工具抛异常LangGraph 的 ToolNode 不会默默吞异常，会抛出来。需要配重试策略，或用 handle_tool_errors=True 把错误变成一条 ToolMessage 交给模型自己处理
上下文爆炸（消息越滚越长）做上下文裁剪，或者把旧消息摘要压缩；也可以只保留最近 N 轮
参数幻觉（编造不存在的参数）用严格 schema + 参数校验，错误时返回明确的提示让模型重试

最后补一句判断："绝大多数生产系统不会用纯 ReAct 扛核心流程， 而是把确定性高的步骤固化成图上的节点，只在真正需要判断的地方留条件边。" 这句话直接引出后面的 S4/S5，面试官会觉得你在做架构思考，而不是在堆功能。

① 一句话目标

把知识库接进来，让回答有据可依。这一版故意做得很简单 —— 它是一条基准线。

③ 代码

第一步：定义检索器的统一接口。这是全项目最重要的设计之一：

python 
class BaseRetriever(ABC):
    """所有检索器都要实现这个接口"""

    @abstractmethod
    def retrieve(self, query: str, top_k: int = 4) -> list[Chunk]:
        """根据查询召回最相关的若干条文本块"""
        raise NotImplementedError

上层只认这一个方法。底层是 BM25 还是向量检索还是 Elasticsearch，上层完全不知道。

第二步：中文 BM25 的分词技巧。BM25 原本是为英文设计的（按空格切词），中文没空格怎么办？

python 
def tokenize(text: str) -> list[str]:
    """中英文混合分词"""
    lowered = text.lower()
    tokens = re.findall(r"[a-z0-9_]+", lowered)      # 英文/数字按连续字母切

    for run in re.findall(r"[\u4e00-\u9fff]+", lowered):  # 中文：切成相邻两字
        if len(run) == 1:
            tokens.append(run)
        else:
            tokens.extend(run[i:i+2] for i in range(len(run) - 1))

    return tokens

# "登录失败" → ["登录", "录失", "失败"]
#                 ↑ 这个片段没意义，但它几乎没有区分度，对排序影响很小

这个技巧叫 bigram（双字片段）。虽然不是真正的分词， 但对关键词检索来说工程上完全够用，而且零依赖 —— 不用装 jieba，不用下载词表。

④ 逐段拆解

为什么要"切块"（chunking）？

  1. 一份文档几万字，整段塞给模型会超长，又贵又慢
  2. 检索粒度越细，越容易精准命中"那一小段真正相关的内容"
  3. 太细又会丢上下文，所以要平衡

项目里的策略是：先按空行分段，再把段落拼到目标长度（400 字），并带上 60 字的尾部重叠。 重叠是为了避免关键信息正好落在切口上被劈成两半。

为什么检索做成"节点"而不是"工具"？

两者都行，取舍不同：

做法优点缺点
做成工具模型自己决定何时检索、用什么 query，灵活模型可能忘记调用，或把 query 写得乱七八糟；流程不可控
做成节点流程确定，每步都在掌控中；检索结果直接落进状态，方便评分、引用、调试灵活性低，不能按需多次检索

判断标准：流程确定的部分用节点，需要模型自主决策的部分用工具。

这个项目里，S2/S3 演示了工具做法，S4 之后切回节点做法。 面试被问到"你为什么不全都用工具"时，这就是答案。

BM25 和向量检索有什么区别？

BM25（关键词）向量检索（语义）
比什么字面有没有相同的词意思像不像
擅长专有名词、错误码、接口名（ERR_502）"上不去网" ↔ "无法完成身份认证"
缺点换个说法就找不到对精确串反而弱；要跑 embedding 模型
成本零依赖、毫秒级要下几百 MB 模型，需要 GPU 更好

生产上的主流做法是混合检索：两路都召回，再用 RRF（倒数排名融合）合并排序。

⑤ 跑起来看什么

输出 
提问：连续输错密码 5 次会怎么样？
命中证据：4 条
回答：
根据知识库中的资料，整理如下：
[1] 来源：02-登录与账号.md ...
以上内容来自上述资料 [1]。

关键看两点：命中的文档对不对，以及 答案有没有标注引用来源。

⚠️ 朴素 RAG 的两个硬伤（这是 S5 要解决的）

硬伤一：检索不到就不管了。用户问的东西知识库里没有，检索返回空列表， 模型还是硬答了一段 —— 这就是幻觉的来源。

硬伤二：检索到垃圾也照用。召回了几段毫不相关的文字， 模型一本正经地总结了一通。用户看起来"有依据"，其实全是错的。

根因在于它的链路是单向的：查询 → 检索 → 生成，中间没有任何反馈环节。 系统不知道自己找错了。

🎯 面试考点

问：朴素 RAG 有什么局限？你会从哪几个方向改进？

答：链路单向、没有反馈是根本问题。改进方向分两头：

  • 往前 —— 优化查询本身：查询重写、同义扩展、多查询（Multi-Query）、HyDE（先编一个假设答案，用答案去检索）
  • 往后 —— 对召回结果做评估：重排序（Rerank）、相关性评分、自纠正（本项目的做法）

追问：chunk_size 怎么定？

答：没有标准答案，要在"召回精度"和"上下文完整性"之间权衡。 我的做法是优先按语义边界（段落、标题）切，其次才按长度切， 并加 10%~15% 的重叠避免信息正好落在切口上。 实际参数要靠评测集来调，不能拍脑袋。

def rewrite_query(state: DocPilotState) -> dict:
    """把口语化的问题改写成更适合检索的表述"""

    ])

④ 逐段拆解

为什么不直接让生成节点"注意别编"，而要单独加个评分节点？

因为这是两件不同的事。生成节点的任务是"把资料组织成通顺的答案"， 它天然倾向于"用上手上的材料"。让同一个调用同时负责"生成"和"自我质疑"， 效果会打折扣。

拆成独立的调用、独立的提示词、独立的职责，是更可靠的做法。 这也符合软件工程里的"关注点分离"。

阈值 6.5 是怎么定的？

拍出来的，然后用一批真实问题跑了一遍看效果 —— 太低了起不到过滤作用， 太高了会频繁触发重写、白白增加延迟和成本。

这里有个很实在的取舍值得在面试里讲：每一次重写都意味着多一次检索 + 多一次评分，延迟大概翻倍。 所以"重写次数上限"既是防死循环的保险，也是成本控制的闸门。

❌ 设计带环的图，第一件事必须回答：怎么退出？

这个项目用了三道保险，缺一不可：

  1. 及格线 —— 分数够了立刻离开循环
  2. 计数器 —— rewrite_count 到达 max_rewrites 强制放行
  3. recursion_limit —— LangGraph 层面的兜底，超过步数直接抛 GraphRecursionError

有人可能会想"第三道就够了"。不够 —— 它是兜底，触发时是异常， 不是正常控制流。用它来管流程，用户看到的会是报错，而不是"资料不足"的友好提示。

一个很容易搞错的细节：评分用哪个问题？

项目里有 original_question（用户原话）和 question（可能被重写过的）两个字段。它们的分工必须分清楚：

节点用哪个为什么
评分节点question（当前 query）要判断"这一轮找的资料够不够回答这一轮的检索意图"，才能反映重写有没有起作用
生成节点original_question用户想知道的是他最初问的那件事，不是我们改写后的检索词

这两行如果搞反，会出现"答案答非所问"或"重写永远不生效"的诡异现象。踩过就知道。

问：你这个项目和普通 RAG 项目有什么区别？

这是必问题。按这个顺序答，层次感最强：

  1. 指出问题：普通 RAG 是单向链，检索质量差就直接崩，系统自己不知道。

_APPROVE_WORDS = {"approve", "yes", "ok", "通过", "同意", "确认"}

def human_review(state: DocPilotState) -> dict:
    """暂停执行，等待人工确认"""

    payload = HUMAN_REVIEW_PAYLOAD.format(answer=answer, issues="...")

        "review_decision": "approve" if approved else "reject",
        "answer": answer if approved else answer + "\n\n⚠️ 人工审核未通过，已被拦截。",
    }

④ 逐段拆解

为什么需要 checkpointer，不能自己存到一个变量里？

因为图暂停之后，进程可能退出。内存里的变量没了，恢复就无从谈起。 检查点把状态序列化写进外部存储，所以理论上可以停几天再恢复。

thread_id 到底是什么？

它就是检查点表里的一个主键。所有存档按 (thread_id, checkpoint_id) 组织。 换个 thread_id 就是另一个平行世界，状态天然隔离，不需要额外加锁 —— 这是 LangGraph 能同时支撑多用户的设计基础。

❌ 用 interrupt 必须知道的两件事

1. 没有 checkpointer 就用不了 interrupt。 状态没地方存，拦截下来就找不回去了，LangGraph 会直接报错。

2. 节点恢复时是「从头重新执行」的，不是从 interrupt() 那一行接着跑。 所以 interrupt() 之前的代码会被再执行一遍。 如果前面有"发消息、扣款、写数据库"这类有副作用的操作，会重复执行 —— 正确做法是把副作用挪到 interrupt() 之后，或者把操作做成幂等。

reflect 节点为什么也要独立出来？

和 S5 里"评分节点为什么要独立"是同一个道理：生成和校验要分开。 让同一个调用既写答案又挑自己的错，效果会打折。换一个调用、换一套提示词、 把任务定义成"挑错"，准确率会明显高一截。

另外这里的 need_human 判断有一条硬规则：

python 
need_human = bool(payload.get("need_human", False))

多轮记忆是怎么实现的？

就靠 messages 字段的 add_messages reducer。 第二次调用同一个 thread_id 时，LangGraph 把上次的消息列表读回来， 新消息通过 reducer 追加在后面 —— 模型于是"记得"之前聊过什么。

注意区分两种"记忆"：这里解决的是同一会话内的对话记忆。 如果要跨会话记住"这个用户偏好简短回答"这类长期信息， 要用另一个东西叫 Store，和 checkpointer 不是一回事。面试常考这个区分。

问：哪些场景需要人机协同？你怎么落地？

场景：高风险操作（转账、删数据、发公告）、合规要求留痕、 低置信度分流、内容对外发布前的终审。

落地要点（这几个点说出来会显得你真做过）：

  • 检查点选型：开发用内存，生产必须用持久化实现（PostgresSaver），否则重启就丢
  • 审核界面的超时与催办策略 —— 人可能几小时不看，要有兜底（超时自动拒绝 or 转下一级）
  • 审核结果要留痕，用于事后审计和模型优化
  • 副作用幂等 —— 这是最容易出事的地方，节点恢复会重跑，别让重复执行造成损失
  • 分级自治：高置信度自动通过、中等置信度通知但不阻塞、低置信度必须人工确认

追问：checkpointer 和 Store 有什么区别？

答：checkpointer 管一个会话内部的状态快照，用 thread_id 索引， 支持暂停恢复和时间旅行；Store 是跨会话的键值存储， 用来记"用户长期偏好"这类应该活得比单次对话更久的信息。两者职责不重叠。

追问：你怎么做 LLM 应用的质量控制？

③ 关键代码：为什么要用 stream 而不是 invoke

python 
def run_graph(payload, *, on_node=None):
    graph = get_graph()
    config = new_thread_config(st.session_state.thread_id)

    # 用 stream_mode="updates" 而不是 invoke —— 每走完一个节点就吐一块
    for chunk in graph.stream(payload, config=config, stream_mode="updates"):
        for node_name, update in chunk.items():
            if on_node:
                on_node(node_name)          # 界面上实时显示"现在走到哪一步"

    snapshot = graph.get_state(config)     # 跑完读回完整状态
    return snapshot.values

invoke 只给你最终结果，中间发生了什么完全看不到。 调试的时候这一点会让你非常痛苦 —— 你不知道是路由判错了、 检索没命中、还是评分虚高。用 stream 就能一步步看着它走。

LangGraph 还支持其他几种流式模式：values（每个超步后吐完整状态）、 messages（吐模型输出的 token，用来做打字机效果）、debug（吐运行时底层事件）。 它们可以在一次订阅里组合使用。

#问题答题骨架

故事一：为什么要把 RAG 从"链"改成"环"

S 背景我先搭了标准 RAG：检索 → 生成。跑测试的时候发现一个问题 —— 用户问"账号被锁了多久才能再登"，检索回来的是另一篇文档，模型照样煞有介事地总结了一通。
T 任务要让系统能发现"这次没找对"，而不是硬编。
A 行动在检索和生成之间插了一个评估节点，让模型给召回证据打分（0~10）。分数低于 6.5 就触发查询重写，换个说法重新检索。同时加了两个保险：计数器限制最多重写 2 次，及格线保证分数够了立刻退出。
R 结果同一个问题，第一次 4.6 分不及格，重写成"账号被锁定 多久才能再登"之后 6.9 分通过，命中了正确文档。我就多了两个节点、十几行代码，系统从"不知道自己找错了"变成了"知道自己找错了"。

故事二：一个 reducer 用错引发的 bug

S 背景我给"执行轨迹"字段用了 add 类型的 reducer，觉得日志嘛，当然要累加。
T 任务加上检查点做多轮对话之后，界面上轨迹越来越长，一轮提问的轨迹里混着上一轮的记录。
A 行动定位到根因：检查点会让同一个会话的状态跨轮保留，而 add 型 reducer 的语义是"旧值 + 新值"，所以历史轨迹一直堆着。改成显式拼接 + 覆盖语义，每轮重置。
R 结果轨迹干净了。更重要的是我总结出一条判断标准：加 reducer 之前先问"这个字段要跨轮累积，还是每轮重置"。历史消息要累积，执行轨迹要重置。

故事三：为什么默认用 BM25 而不是向量检索

S 背景一开始想直接用 Chroma + 中文 embedding 模型，结果部署时卡在下载几百 MB 的模型上，环境问题耗掉了大半天。
T 任务要让人能在几分钟内看到效果，而不是先花半天配环境。
A 行动把检索层抽象成统一接口 BaseRetriever，默认实现换成 BM25 —— 纯 Python、零依赖、装完就能跑。中文用双字片段（bigram）代替分词，不用装 jieba。向量检索保留成可选实现，改一行配置就能切。
R 结果从"装完依赖到看到第一个正确答案"从半天缩短到 30 秒。而且这个"可插拔"的设计本身就是加分项 —— 它证明我在做架构上的权衡，而不只是把功能堆上去。

故事四：让系统能"停下来等人"

S 背景答案里出现"建议""必须"这类表述时，一旦答错后果比"答不上来"严重得多。需要在交付前加一道人工闸门。
T 任务让图能暂停、等人决策、再恢复执行，而且暂停期间状态不能丢。
A 行动用 interrupt() 在审核节点处暂停，配 InMemorySaver 把状态持久化，用 thread_id 作为恢复的线索，恢复时传 Command(resume=decision)。
R 结果命令行和界面里都能完整演示"暂停 → 人工审批 → 继续"的流程，approve 和 reject 两条路径都覆盖了测试。顺带踩了一个坑并解决：节点恢复时会从头重跑，所以 interrupt() 之前不能放有副作用的操作。

故事五（如果被问"你最大的收获是什么"）

不要答"学会了 LangGraph 的 API"。答这个：

"最大的收获是意识到，在做 LLM 应用时，"让模型更强"往往不是最优解，"让系统能发现自己的错误"才是。

我加的那两个节点（评分、重写）没有让模型变聪明一点，但整个系统的可靠性上了一个台阶。 这个思路我以前只在工程里见过（比如编译器的静态检查、数据库的事务）， 没想到在 AI 应用里同样成立。"
